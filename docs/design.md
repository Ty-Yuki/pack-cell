> **レイアウトと流れの最新は §16**（§2・§4・§10 の記述を置き換える）。座標・寸法の確定値は `src/pack_cell/layout.py`

## 0. 一言でいうと

ネットスーパーの出荷場を想定する。オペレータが自然言語で注文と詰め方（「卵は最後に」「冷たいものはまとめて」）を伝えると、次の流れで箱詰めする。

1. ローカルLLMが指示を**制約**に変換する。
2. 検証器と配置計画器が、**物理的に崩れない積み付け計画**と**積み順DAG**を作る。
3. 2台のUR5e（吸着ハンド）が**協調スケジューリング**で並列に作業する。空箱の供給、棚からのピッキング、積み付け、蓋閉め、出荷までを行う。

欠品・途中の追加注文・把持失敗が起きても再計画して完遂する。

### 設計原則

- **LLMは解釈と提案だけを担う。** 位置・順序・軌道はアルゴリズムが決め、物理ルールは検証器が保証する。LLMの誤りがロボットに届かない構成にする。
- **制御・計画のコアはROSに依存しない純Pythonで書く。** pytestとオフライン実行で速く検証できるようにする。
- **シミュレーション時刻は `/world/<w>/stats` から取る。** 録画は制御とは別のプロセスで行う。

## 2. セルのレイアウト

### 2.1 上面図（暫定、単位 m、原点＝梱包台中心の床面）

```
                         +y
                          ^
        [蓋置き場]         |   棚L（加工食品・日用品, ArmA主担当）
        (-0.80,+0.40)      |   x∈[-0.45,0.00], y∈[0.30,0.66]
                      +---------+
                      |c1 c2 c3*|  * = 両アーム到達可（共有スロット）
                      +---------+
 [出荷台]   [ArmA]       [梱包台/箱]       [ArmB]   [仮置き台]
 (-0.95,0) (-0.45,0)      (0,0)          (+0.45,0)  (+0.80,0)
                      +---------+
                      |*c3 c2 c1|
                      +---------+
        [製函機出口]       |   棚R（日配品, ArmB主担当）
        (-0.75,-0.40)      |   x∈[0.00,0.45], y∈[-0.66,-0.30]
                          v
                         -y
```

- **ArmA**: 台座（高さ0.70）上の base (-0.45, 0, 0.70)、+x 向き。
- **ArmB**: base (+0.45, 0, 0.70)、-x 向き。
- **梱包台**: 天板 z=0.70、x∈[-0.25,0.25]、y∈[-0.20,0.20]。箱は中心に置く（長辺がx方向）。箱を置いたら位置決めストッパ（world↔箱の DetachableJoint）で固定する。
- **共有ゾーン**: 梱包台の真上の柱状領域（x∈[-0.25,0.25]）。同時に入れるのは**1台だけ**（mutex）。
- **待機点**: 各アームがゾーン外で品物を持って待つ位置。A は (-0.30, 0, 1.00)、B は (+0.30, 0, 1.00)（暫定）。
- **棚**は点対称に配置する。それぞれ3段のひな壇で、各段3列、列ピッチ0.15。
  - 段1（手前）: y=±0.36、天面 z=0.72
  - 段2: y=±0.48、天面 z=0.80
  - 段3（奥）: y=±0.60、天面 z=0.88
- **到達性の目安**: 吸着ツール（長さ0.12）を下向きにしたとき、水平距離0.75以内なら届く。初期 で到達性マップを計算して確定する。

### 2.2 棚のスロット割り当て（暫定）

列 c1 が主担当アームに最も近く、c3（*）は共有スロット（両アームが到達できる）。

| | c1 | c2 | c3* |
|---|---|---|---|
| **棚L 段1** | 水2L（c1〜c2の2列） | ← | 缶詰 |
| **棚L 段2** | 米2kg（c1〜c2の2列） | ← | ポテトチップス |
| **棚L 段3** | 台所用洗剤 | 缶詰 | ポテトチップス（*対象外。Bは届かない） |
| **棚R 段1** | 卵パック（c1〜c2の2列） | ← | 牛乳1L |
| **棚R 段2** | 食パン（c1〜c2の2列） | ← | 豆腐 |
| **棚R 段3** | アイス | 低脂肪乳1L | 空き |

- 品物の初期位置には乱数でずれを入れる（xy ±2cm、yaw ±10°）。カメラで検出してから取る。
- 欠品はシナリオ設定でスポーンしないことで表現する。在庫はDBではなく**カメラの検出結果**から判断する。
- 注文ごとに、使った品物を補充（再スポーン）する。WMSによる補充を想定する。

### 2.3 箱と蓋

- 箱: 外寸 44×30×23.5 cm、内寸 42×28×22 cm、質量 0.3 kg。
- 箱内は**14cm角のセル 3（x）×2（y）を2層**の格子として扱う。品物は12cm幅なので、セル内に2cmのクリアランスがある。
- 蓋: 44×30×1 cm。蓋置き場に3枚を積んでおく。
- 製函機出口: 空箱が1つずつ出てくる（ArmA が取ると次がスポーンする）。
- 封函: 蓋を載せたら蓋↔箱と、中身↔箱を DetachableJoint で固定する（テープ封函の簡略化）。そのうえで ArmA が蓋の上面を吸着し、出荷台へ移す。中身の安定性は封函前に判定する。

### 2.4 カメラ

| 名前 | 位置 | 用途 |
|---|---|---|
| `cam_shelf_l` / `cam_shelf_r` | 各棚の真上 z≈1.6、下向き | ArUco の検出（ピッキング位置、在庫の確認） |
| `cam_box` | 箱の真上 z≈1.5 | 配置後の確認、把持失敗の検知、動画 |
| `cam_overview` | 斜め上の俯瞰 | 動画のメインカット |
| `cam_side` | 横から | 積み重なりが見えるサブカット |

## 4. 全体の流れ

```
[チャット] 注文文
   │
   ▼
① 指示の解析（LLM）          文 → OrderSpec(JSON)：品目・数量・制約（explicit / implicit）
   │
   ▼
② 在庫照合（知覚）           棚カメラの検出結果と照合 → 欠品なら ⑥ へ
   │
   ▼
③ 検証＋配置計画（アルゴリズム） ハイトマップ探索 → PackPlan（各品のセル・層・向き・z）
   │   └─ 不可能・矛盾 → 理由をLLMへ返して修正（最大2回）→ だめならオペレータに確認
   ▼
④ 積み順DAGの生成           支持関係＋順序制約 → 先行関係グラフ
   │
   ▼
⑤ 2腕の協調実行             空箱供給 → 取得/待機/配置（ゾーン排他）→ 蓋 → 封函 → 出荷
   │   ├─ 把持失敗 → 再検出して再試行 → 2回失敗したら他方のアームへ再割り当て
   │   └─ 追加注文 → ⑥
   ▼
⑥ 再計画                    置いた品を固定条件として ③ をやり直す → 不可能なら最小限の積み直し案と別箱案
   │                         → LLMが状況を説明し、オペレータが選択 → ④⑤ へ
   ▼
⑦ 完了判定（真値）           全品が箱内か・傾き5°未満か・制約を満たしたか → ログ・動画
```

## 5. 言語理解と制約

### 5.1 OrderSpec（LLMの出力スキーマ）

llama.cpp の `response_format: {type: "json_schema"}` を使い、出力を文法で縛る。temperature は 0 にする。

```json
{
  "items": [{"sku": "rice", "qty": 1}, {"sku": "canned", "qty": 2},
            {"sku": "egg", "qty": 1}, {"sku": "bread", "qty": 1}],
  "constraints": [
    {"type": "last", "args": ["egg"], "source": "explicit", "hard": true,
     "evidence": "卵は最後に入れて"},
    {"type": "nothing_on", "args": ["bread"], "source": "implicit", "hard": false,
     "evidence": "食パンは潰れやすい"}
  ],
  "unknown_items": [],
  "clarification": null
}
```

### 5.2 制約の語彙

| type | 引数 | 意味 |
|---|---|---|
| `before` | a, b | a を b より先に箱へ入れる |
| `first` / `last` | a | 最初・最後に入れる |
| `layer` | a, `bottom`\|`top` | 指定した層に置く |
| `not_on` | a, b | a を b の上に載せない |
| `nothing_on` | a | a の上に何も載せない |
| `group` | [a, b, ...] | 同じ層で4近傍が連結するように隣接させる（例: 冷たいものをまとめる） |
| `separate` | a, b | 隣接させず、上下にも重ねない |

- `explicit`（ユーザーが言ったこと）は hard、`implicit`（LLMが常識から補ったこと）は soft を既定にする。
- **物理ルールはLLMに任せず、検証器がカタログから必ず適用する。**
  1. 2層目の品物は、真下が埋まっていること（全面支持）。支持面の高さの差は1cm以内。
  2. 各品物の上に載る質量の合計が、その品物の耐荷重以下であること。
  3. 積んだ高さが22cm以下であること。
  4. 非食品（洗剤）は食品の上に置かない。
  5. 箱の容量（12セル）。

### 5.3 プロンプトの方針

- システムプロンプトに、カタログ（名前、別名、属性）、制約の語彙、少数の例（3〜4件）を入れる。
- 「位置は決めない」「カタログにない品は `unknown_items` に入れる」「暗黙の制約には evidence を書く」を明記する。
- Qwen3 系は思考モードを切る（`chat_template_kwargs: {enable_thinking: false}`）。応答時間を測り、精度が落ちるようならオンにする。
- **record / replay モード**: LLMの応答をハッシュでキャッシュし、撮り直しやテストでは replay する。結果の再現性と、オフラインでの検証を確保する。

### 5.4 LLMを呼ぶ3つの場面

| 呼び出し | 入力 | 出力 |
|---|---|---|
| `parse_order` | 注文文、カタログ | OrderSpec |
| `repair` | 前回の OrderSpec、検証器の違反リスト（理由付き） | 修正した OrderSpec、または `clarification`（ユーザーへの質問） |
| `explain_options` | 状況（欠品・追加）と、**アルゴリズムが列挙・検証済みの選択肢** | 選択肢の順位、日本語の説明文（表示用） |

欠品時の代替候補は、LLMが常識で提案する（牛乳 → 低脂肪乳）。それを検証器が「在庫あり・寸法と配置で成立」と確認してから選択肢にする。

## 6. 配置計画（ハイトマップ探索）

- **状態**: 3×2セルそれぞれについて「上面の高さ・その列に載っている品物」を持つ。
- **探索**: 品物を「大きい・重い順」に並べ、各品について候補（層、セル、向き）を総当たりする。物理ルールと hard 制約で枝刈りしながら深さ優先で探索する。品物は最大8点程度なので、全探索でも数十ms。
- **スコア**（soft の評価）: 重心の低さ、`group` の連結度、implicit 制約の充足、層の上面の平坦さ。
- **出力**: PackPlan。各品物の `cell`、`layer`、`yaw`、目標姿勢（箱座標の x, y, z）。
- **不可能なとき**は、満たせなかった制約と物理ルールを**理由付きで**返す（例: 「egg に water(2.1kg) が載り、耐荷重 0kg を超える」）。これを LLM の repair とオペレータへの確認にそのまま渡す。

### 再計画（追加注文）

1. 箱内の品物を固定条件にして探索する。
2. 解がなければ、**上から k 個（k=1, 2）を取り出す**ことを許して再探索する。コストは追加のピック回数とする。
3. 選択肢として「最小限の積み直し」「別箱に分ける」を出す（どちらも検証済み）。LLM が説明文を付けてオペレータに示し、ユーザーが選ぶ（評価ではオートで先頭を選ぶ）。

## 7. 積み順DAGと2腕スケジューリング

### 7.1 DAG

- **ノード**: `SUPPLY_BOX`、各品物の `PLACE(i)`、`LID`、`SEAL`、`SHIP`。
- **辺**:
  - 支持関係（下の品 → 上の品）
  - 順序制約（`before`、`first`、`last`）
  - `SUPPLY_BOX` → 全品物 → `LID` → `SEAL` → `SHIP`
- 制約から閉路ができたら矛盾として検証器が弾く。

### 7.2 タスクの分割とアームの割り当て

- 1つの品物は **`FETCH(i)`**（棚から取って待機点まで）と **`PLACE(i)`**（ゾーンに入って置き、出る）に分ける。
- `FETCH` は先行関係を待たずにいつでも始められる（**先取り**）。`PLACE` は「先行品がすべて置かれた」かつ「ゾーンを取得できた」ときだけ実行する。
- 割り当て:
  - 主担当アームしか届かないスロット → そのアーム
  - 共有スロット → 「完了見込みが最も早い」アーム（所要時間の見積もりは関節空間の距離と速度上限から計算し、実測で校正する）
- **ゾーンの付与規則**: 待っているアームのうち、DAG のトポロジカル順で先に置くべき品を持つほうに付与する。各アームが持てるのは1個までで、トポロジカル順に従って付与するので**デッドロックは起きない**。
- `SUPPLY_BOX`、`LID`、`SEAL`、`SHIP` は ArmA が担当する。そのあいだ ArmB は次の注文の品物を先取りできる（ただし同時に持てるのは1個まで）。

### 7.3 比較する戦略（評価用）

| 戦略 | 内容 |
|---|---|
| S0 逐次 | どちらかが動いているあいだ、もう一方は停止する（1台相当の基準） |
| S1 固定分担 | 棚L は A、棚R は B が担当。先取りはしない（先行品が置かれてから取りに行く） |
| S2 提案手法 | 先取り＋共有スロットの動的割り当て＋トポロジカル順のゾーン付与 |

スケジューラは、所要時間モデルを使う**オフラインの離散イベントシミュレーション**でも動かせるようにする。Gazebo での実測と比べて、モデルの妥当性も示す。

## 8. ロボット制御と知覚

### 8.1 アーム

- UR5e: `ur_description` の xacro から URDF を生成し、SDF に埋め込む。各関節を `JointPositionController` で動かし、関節状態は `JointStatePublisher` で取る。
- **IK**: UR の解析解（8通り）から「現在の姿勢に最も近く、肘が上」の解を選ぶ。
- **軌道**: 経由点（上空 → 接近 → 吸着/解放 → 上昇）の間を関節空間で補間し、台形速度で 50Hz で指令する。速度上限は1.0 rad/s。
- **スキル API**（アームごとに ROS 2 action `ExecuteSkill`）: `home`、`pick(item_id, pose)`、`move_to_staging`、`place(pose)`、`pick_box`、`place_box`、`pick_lid`、`place_lid`。
- **吸着の模擬**: ツール先端が品物の上面中央から xy 1.5cm、z 1cm 以内にあれば、DetachableJoint の attach を送る。吸着できたかどうかは「圧力センサ」の代わりにフラグで返す。
  - DetachableJoint は（アーム × 対象物）の組ごとに SDF に定義するので、ワールド生成スクリプトで自動生成する（約60個）。**ロード直後は全組が溶接された状態になるため、初期化で必ず全て detach する。**
- **失敗の注入**: シナリオ設定で、指定した品・回数の吸着を失敗させる（確率指定も可）。

### 8.2 知覚

- 棚カメラの画像から OpenCV の ArUco を検出し、既知の内部パラメータと外部パラメータを使って `solvePnP` で 6D 姿勢を求める。
- 出力: `/perception/items`（ID、SKU、姿勢、信頼度）。
- 在庫照合: 注文の SKU が検出結果にあるかを確認する。
- 把持の確認: 持ち上げた後に吸着フラグを確認し、棚カメラで「その品物がまだ棚にあるか」を見る。

## 10. デモシナリオ（初期案）

### シナリオ1: 基本

> 「米と缶詰を2つ、卵と食パンをお願いします。卵は最後に入れてください。」

1. A が空箱を供給する。そのあいだに B が食パンを先取りする。
2. 下段に米と缶詰×2、上段に食パン（缶詰の上）と卵（米の上、最後）を置く。
3. A が蓋を載せ、封函して出荷する。

見どころ: 暗黙の制約（パンや卵の上に載せない）、支持面の高さが揃う配置（米8cmの上に卵）、先取りによる並列化。

### シナリオ2: 欠品・追加注文・把持失敗

> 「牛乳と豆腐とアイス、ポテトチップス、缶詰。冷たいものはまとめて。」

1. **欠品**: 棚カメラに牛乳が映っていない。LLM が低脂肪乳を提案し、オペレータが承認する。
2. 実行中に缶詰の吸着が失敗する（注入）。再検出して再試行し、そのあいだ B は作業を続ける。
3. ポテトチップスを下段に置いたあとで**追加注文**「やっぱり水も1本追加して」が来る。
   - 下段の空きは1セルで、2セル幅の水（2.1kg）が入らない。上段に置くと、潰れやすい品の上に載ってしまう。
   - 選択肢: ① ポテトチップスを一度仮置きし、水を下段に入れ、ポテトチップスを水の上に戻す（追加2ピック） ② 水だけ別の箱にする。
   - ① を選んで実行する。
4. 蓋を閉め、封函して出荷する。

見どころ: 物理制約を理解したうえでの最小限の積み直し、説明付きの選択肢、失敗からの回復。

> 品物の配置はプランナーが決定的に出すので、実装中に実際の出力を見て、シナリオが成立するように注文内容を微調整する。

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| 積んだ品物が滑ったり揺れたりする | 摩擦 μ=0.8、ステップ 1ms。置く直前は 2cm/s に減速し、高さ 5mm で離す。箱はストッパで固定する |
| 2台の UR が名前空間や制御で衝突する | ROS の ros2_control は使わず、Gazebo の関節コントローラをモデル名で区別して直接指令する |
| コンテナ内でカメラの描画（EGL）が動かない | 初日に確認する。だめならホスト側で `gz sim` を動かし、ROS ノードだけをコンテナで動かす |
| LLM の出力が揺れる、または遅い | JSON スキーマで縛る、temperature 0、思考オフ、record/replay、タイムアウト時はルールベースのパーサにフォールバック |
| 到達できない、または特異点 | 初期の到達性マップでスロットを確定する。経由点には肘が上の解だけを使う |
| DetachableJoint の数が多く起動が重い | 生成スクリプトで（アーム × 実際に掴む品）だけに絞る。補充はスポーンではなく位置の再設定で行う |
| 間欠的な失敗で実験が止まる | タスク単位でタイムアウトと再試行を入れる。失敗は除外せずに件数を報告する |

## 14. 実装で変えた点（v0.2）

実装と動作確認の過程で、次の点を設計から変えた。いずれも理由はシミュレーション上で観測した不具合。

| 項目 | v0.1 の設計 | 実装 | 理由 |
|---|---|---|---|
| 関節の制御 | Gazebo の関節コントローラに直接指令 | `gz_ros2_control` + `scaled_joint_trajectory_controller`（名前空間 `/arm_a`, `/arm_b`） | 2台構成での動作実績があり、軌道の追従誤差を検出できる |
| IK | 解析解 | 減衰最小二乗（数値）＋ 2πの等価角を可動範囲内へ正規化 | 正規化しないと肩の旋回が ±2π を超えて止まる |
| 吸着ノズル | 0.12m | 0.20m | 短いと、箱の底や1段目に置くとき手首が箱の縁に当たる |
| 箱 | 内寸 42×28×22cm | 外寸 44×30×21.5cm（内高 20.5cm） | 箱の底を吸って運ぶとき、手首と縁のすき間を確保する |
| 棚 | 段差 8cm（天面 0.72/0.80/0.88） | 段差 4cm（0.72/0.76/0.80） | ノズルを伸ばしたため、高い位置で届く範囲が狭くなった |
| 搬送高さ | — | 品物 1.06m、箱 0.95m | 箱は両アームの肘より十分下を通す |
| 空箱・蓋 | 製函機出口 -y、蓋 +y | 製函機出口 +y、蓋 -y | 箱の搬入中も ArmB が棚R（-y）で先取りできる。蓋は全品を置いた後なので ArmB は手空き |
| 出荷台 | (-0.95, 0) | (-1.10, 0)、箱の向きはそのまま | 蓋置き場と重なり、箱が蓋に乗り上げて傾いた |
| 封函 | 蓋↔箱・中身↔箱を DetachableJoint で固定 | 固定しない。蓋の上から箱ごと吸着して運ぶ | 「ArmA↔箱」「ArmA↔蓋」「箱↔蓋」が閉ループになり、起動直後に物理計算が発散する |
| 待機点 | 共有ゾーンの外 | ベースの斜め後ろ 0.39m の -y 側（A は製函機出口の空箱の上を避ける）。品を持って待つ位置は「取った棚の側」 | ベースに近いと IK が腕を頭越しに折り返し、肘が梱包台の上空に出る。側をまたぐ移動はベースの前を通るので、ゾーンを持つ行動の中だけで行う |
| 干渉の規則 | ゾーンの mutex | ゾーン + 棚ごとのロック + 箱・出荷（+y）と蓋（-y）の側の占有。共有スロット（c3）から取るときは自分の棚でもゾーンを占有し、相手の棚から取るのは相手がその側で品を持って待っていないときだけ | 共有スロットは x=±0.075 で、実はゾーンの幅の中にある。そこで作業する腕が、置きに来た相手の腕や待機中の品と当たった |
| 制約の語彙 | 7種 | `on(a, b)`（a を b の上に載せる）を追加 | 「卵の上に水を載せて」のような指示を表せないと、物理的な矛盾を検出できない |
| 配置の選び方 | 物理コスト最小 | 物理コストの上位40候補を、2腕スケジュールの所要時間（DES）で選び直す（同時最適化） | 配置で積み順の依存がほぼ決まり、スケジューラだけでは並列化に限界がある |
| 知覚 | 6D 姿勢 | xy と yaw は ArUco、高さは棚の段とカタログから | ArUco の奥行きは約5mm低く出る。xy の誤差は 1.6mm 以下、yaw は 0.1° 以下 |
| 隠れ | — | 腕でマーカーが隠れたら、最後に検出した位置を使う | 棚の上で待機する腕が天井カメラを遮る |
| 追加注文の解釈 | 注文と同じプロンプト | 元の注文を文脈に渡し、追加分だけを返させる | 例文の品が混ざって解釈された |
| 起動 | 2台同時に待機点へ | 吸着ジョイントの解除を3巡送り、1台ずつ「旋回してから腕を下ろす」。動けなければ解除の再送と初期配置の復元 | 解除命令の取りこぼしで品・箱がアームに溶接されたまま残り、間欠的に動けなかった（旧実装の「起動時の間欠的な失敗」もこれと考えられる） |
| 先取りした品の待ち方 | ゾーンの外の待機位置 | 空箱が来る前に ArmB が先取りした品は、ArmB の後方の待機点で持って待つ | 梱包台寄りで長い品（食パン）を持っていると、旋回して運ばれてくる空箱と当たった（Web UI の確認で発見） |
| 在庫 | 棚の検出結果 | スロット判定の許容 7cm。両アームが進めない状態が続いたら撮り直し、60秒進まなければエラー | 起動時に品が数cm押され、在庫から抜けて停止した |

## 16. 出荷レーン型への作り直し（v0.4）

v0.3 までは「梱包台の上の箱に詰め、蓋を載せ、ArmA が箱ごと出荷台へ運ぶ」構成だった。封函が「蓋を載せるだけ」で実際の出荷場と離れていたため、レイアウトを出荷レーン型に作り直した。§2（レイアウト）・§4（全体の流れ）・§10（デモシナリオ）・§13（動画の構成）の記述は、この節で置き換える。

### 16.1 レイアウトと流れ

```
        [棚L 上流]   (ArmA)   [棚L 下流]
                       |
 製函機 ==[待機]==[梱包位置]==[封函機]==========> 出荷(画面の外へ)
   入口コンベヤ     梱包コンベヤ     出口コンベヤ
                       |
        [棚R 上流]   (ArmB)   [棚R 下流(奥の段は仮置き台)]
```

- 中央を x 方向の直線コンベヤが通り、ArmA（+y 側）と ArmB（-y 側）が両側から挟む。棚は各アームの上流側と下流側に1台ずつ（2段）。
- コンベヤは入口・梱包・出口の3区間で、区間ごとに動かす・止める（Gazebo の TrackController。加減速 0.3m/s² で中身はずれない）。見た目でも区間の境目に隙間とローラーを付け、梱包区間はレールの色を変えた。
- 流れ: 製函機が注文に合わせたサイズの空箱を出す → 待機位置 → 梱包位置で止めて位置決め → 2台で詰める → 封函機でフラップを閉じる（テープは長いフラップの表に付いていて、閉じると上になる）→ 出口コンベヤで画面の外へ。
- 空箱の搬入・蓋・出荷は ArmA の仕事ではなくなり、2台とも取り出しと箱詰めに専念する。蓋と蓋置き場・出荷台は廃止した。
- 連続注文: 次の注文の解釈・欠品の確認・箱の選択・製函は、今の注文を詰めている間に進める。詰め終えたら、封函・出荷と次の空箱の搬入を同時に行う。出口コンベヤは1箱ずつ使う。

### 16.2 箱のサイズ

| サイズ | 外寸 | 主な用途 |
|---|---|---|
| 小 | 32×30×16cm | 卵・食パン・缶詰・豆腐・アイスなど |
| 中 | 40×30×22cm | 米・水・牛乳を含む注文 |
| 大 | 44×32×26cm | 背の高い洗剤（21cm）を含む注文・品数の多い注文 |

計画器（`Planner(cat, box)`）は箱の内寸をインスタンスに持ち、小 → 中 → 大の順に配置を試して、入る最小の箱を選ぶ（`Cell.choose_box`）。箱は種類ごとに数個を置き場に用意し、製函機が頼まれたサイズを出す。再計画（追加注文）は今の箱のまま行う。

### 16.3 実装で変えた点

| 項目 | v0.3 | v0.4 | 理由 |
|---|---|---|---|
| アームの位置 | x=±0.45 で向かい合う | (0, ±0.40)。コンベヤを挟んで向かい合う | コンベヤを中央に通すため |
| 肩の旋回角の窓 | 境目はベースから見て真右 | 境目は真後ろ（コンベヤと反対側。何もなく通る必要がない） | 上流側と下流側の棚の行き来は必ずベースの前を通る |
| 反対側の棚への移動 | 取り出しの行動の中で | 独立した行動（cross）にし、共有ゾーンはその移動の間だけ占有する | 取り出しの間ずっとゾーンを持つと、相手が箱に置けない |
| 待機点 | ベースの斜め後ろ 0.39m | 品を持って待つ点はベースの真横やや前 0.40m（上流側/下流側） | 後ろ寄りだと反対側へ移る旋回が大きい |
| IK の解の選び方 | 現在の姿勢に近い解 | 肩の旋回が目標の方向を向く解だけを採る | 肩を反転させて頭越しに折り返す解が選ばれ、上腕がコンベヤの上空に張り出して相手と当たった |
| 在庫 | 品目ごとに1個 | 品目ごとに重ねる（米・缶詰・アイス）か並べる（それ以外）で2個ずつ。牛乳は最後の1本。出荷した品は棚に戻さない | 連続注文で在庫が尽きないように。補充の瞬間移動をなくす |
| 重ねた品 | — | 検出した高さから段数を求めて吸着の高さを決め、上に品が載っている品は取り出し元にしない。上の品を取ったら棚を撮り直す。隠れた下の品は棚の管理情報から数える | 下の品は上の品に隠れてカメラに映らない |
| 欠品 | 注文を始めるときに確認し、LLM の代替をそのまま採用 | 注文を解釈した時点で、今詰めている注文が使う分を差し引いて確認する。LLM が代替を提案し、オペレータが承認してから反映 | 本当に在庫が尽きる流れにし、代替の決定を人に委ねる |
| 追加注文の選択 | LLM の推奨を採用 | LLM が推奨し、オペレータが返信で案を選べる。推奨の欄と説明の文が食い違ったら聞き直す | 推奨と説明が食い違うことがあった。最終判断は人 |
| 仮置き台 | 固定の3か所 | ArmB の下流側の棚の奥の段に、品の幅に応じて詰めて並べる | 固定の位置では幅の広い卵パックが隣の品と重なった |
| 所要時間の範囲（評価） | 空箱の搬入から出荷まで | 注文の開始から全品を詰め終えるまで（空箱が届くまでの待ちを含む） | 搬入・封函・出荷はコンベヤと封函機の仕事で、アームの協調とは独立 |
| LLM の応答の再生 | sim 時刻の上で即時 | 録画では、記録した応答を実際の所要時間だけ sim 時刻で待って返す | 動画の時系列（送信 → 考え中 → 返信 → 計画 → 動作）を本物にする |
